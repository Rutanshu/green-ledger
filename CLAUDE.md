# CLAUDE.md — Green Ledger conventions

Read `SPEC.md`, `UX.md`, and `ARCHITECTURE.md` before writing code. They are the contract.

## Non-negotiables
1. **Emissions arithmetic lives only in `lib/calc/`.** Pure functions. No Prisma, no fetch, no `Date.now()`, no `Math.random()`. If a UI component multiplies anything by an emission factor, that's a bug.
2. **Every number is traceable.** An `EmissionRecord` stores `quantity_normalised`, `factor_value`, `factor_unit_*`, `factor_source`, `factor_version`, `gwp_value`, `gwp_set`, `unit_conversion_factor`, `consolidation_share`, and `calc_engine_version` — not just the result.
3. **Factors are immutable once referenced.** Corrections create a new version with a new `valid_from`. Recalculation is explicit, user-triggered, audit-logged, and refused on locked periods.
4. **Units are a type (`UnitCode`), never a string.** Cross-dimension conversion (L → GJ) is a *fuel property*, not a unit conversion.
5. **No floats.** `Decimal` end to end. Round only at display/export.
6. **Every tenant query is org-scoped** — Prisma extension *and* Postgres RLS.
7. **Audit events are written in the same transaction** as the change they describe.
8. **Locked periods are immutable.** Corrections go through restatement.
9. **A question cannot be published with a broken or ambiguous factor binding.** `Test binding` must pass. A form that silently records zeros is the worst possible bug in this product.
10. **`visible_if` is evaluated by ONE pure function** used by both client and server. Never reimplement the logic in a component.
11. **An Answer is what a human typed; an ActivityRecord is the accounting record.** `projectAnswer` maps one to the other. Never let UI code write an ActivityRecord directly.
12. **No hardcoded user-visible strings.** Every label goes through `resolveLabel()` / the `<Label>` component. A string literal rendered to a user is a bug — there's a lint rule. Codes are the system's; labels belong to the org and can be renamed at six levels of specificity without any number changing.
13. **The product is industry-neutral.** No vertical assumptions in schema, seeds, or copy. If a concept only makes sense for one industry, it belongs in an org's own vocabulary, not in the codebase.

## Definition of done for any calc change
- [ ] Pure function, no side effects
- [ ] Zod schema on every input boundary
- [ ] Unit tests including: superseded-factor reproducibility, mid-year factor split, unit-mismatch throws, Scope 2 dual-basis
- [ ] Migration included if the schema moved
- [ ] `calc_engine_version` bumped if the formula changed

## Prompt shape for build sessions
State: the stack, the exact files to touch, the acceptance criteria, and what not to change.
> "Add the `EmissionRecord` model per SPEC.md §3.5. Files: `prisma/schema.prisma`, `lib/calc/emissions.ts`, `lib/calc/emissions.test.ts`. Include the migration, Zod validation, and a test that a diesel record with a superseded factor still recalculates to its original value. Don't touch `lib/auth/`."

## After every feature
Run this prompt: *"Review this diff as a skeptical senior engineer. What breaks at 100,000 records, at a mid-year factor update, or when two factors match equally well?"*

## Naming
- DB: `snake_case`, plural tables. TS: `camelCase` vars, `PascalCase` types.
- Enums are DB enums, mirrored as TS union types generated by Prisma. Never a free-text status column.
- Money and quantities: `Decimal(20,6)`. Factors: `Decimal(24,12)`. Emissions: `Decimal(24,6)`.

## Commits
Small and revertible. One migration per commit. Message: `feat(calc): mid-year factor split` style.
